# 浏览器报名代填（两阶段）

核心思路：用户把所有报名材料丢进一个文件夹，先解析文件夹生成核对过的"资料包"，之后每次报名只需打开网页，从资料包取值填写。可逆的准备工作自主完成，有后果的动作交还用户。

判断当前阶段：文件夹里没有 `registration-profile.yaml` 就从第一阶段开始；已有资料包（或用户说"用我上次的资料"）直接进第二阶段。

## 第一阶段：解析材料文件夹，建立资料包

请用户把手头所有报名相关材料放进一个文件夹（或直接指定一个已有文件夹），常见材料：身份证扫描件、证件照、简历、学历学位证书、学籍/学历验证报告、成绩单、旧的报名表、获奖证书。然后：

1. 扫描文件夹，列出识别到的文件，跳过明显无关的文件并说明。
2. 逐个解析：PDF 用文本提取（pdftotext / PyPDF），扫描件和图片用视觉能力读取；`.docx` 用 pandoc 或 python-docx；`.xls/.xlsx` 用 openpyxl 或 pandas。旧报名表最有价值，字段最全，优先解析。
3. 对照 [references/common-fields.md](references/common-fields.md) 的常见报名字段清单提取信息，材料里没有的字段标为"待补"，不要编造。
4. 同一字段在多份材料里不一致时（如两份简历电话不同），标记冲突问用户，不要自行取舍；重要字段记录信息来自哪份文件。
5. 规范化日期、电话、地址格式，但不改变含义。
6. 附件文件（证件照、扫描件等）按用途登记**绝对路径**，顺带检查证件照的像素、大小是否符合常见报名规格（见字段清单），不达标提前提醒。
7. 按 [assets/profile-template.yaml](assets/profile-template.yaml) 的结构生成 `registration-profile.yaml`，默认保存在材料文件夹内，让所有报名相关内容集中一处。

写入前提醒：这是明文文件，身份证号等敏感字段如果用户不想落盘，可以标记为"现场提供"。**绝不写入**：密码、短信/邮箱验证码、银行卡号、支付信息、cookie、安全问题答案。

生成后把资料包摘要和"待补清单"给用户核对，用户确认无误后第一阶段结束。之后资料包就是唯一事实来源，第二阶段不要再让用户重复已有信息；用户补了新材料就重新解析增量更新。

## 第二阶段：打开网页自动填写

前置：读取资料包文件。然后明确本次任务：

- 目标网址或机构名称（核对域名与用户说的一致，可疑域名先停下确认）
- 报名目标与截止时间
- 网页要求但资料包里没有的字段（汇总成一组问题一次问完）
- 需要用户临场决定的选项（场次、考点、是否同意某项声明等）

### 浏览器工具

- **Claude Code**：默认用内置 Browser 面板（`mcp__Claude_Browser__*` 工具，`navigate` 打开、`read_page` 读结构、`form_input` 填写）；需要已登录态时改用 Chrome 扩展（`mcp__claude-in-chrome__*`）。
- **Codex / Cursor / Antigravity**：用 Playwright MCP 操作浏览器（`browser_navigate` 打开页面、`browser_snapshot` 读页面结构、`browser_type`/`browser_fill_form` 填写、`browser_click` 点击、`browser_file_upload` 传文件）。需要复用用户真实 Chrome 登录态时用 extension 模式（配置见 [docs/BROWSER_MCP_SETUP.md](../../../docs/BROWSER_MCP_SETUP.md)）。
- 浏览器控制不可用时，如实告知需要先配置什么，不要声称已经操作了页面。

### 填写流程

1. 打开目标页，先通读报名须知：资格条件、截止时间、费用、所需材料、重要声明。发现疑似不符合资格、意外收费、要求可疑时，先报告再继续。
2. 用 `browser_snapshot` 获取表单结构，按**字段含义**（不只是标签文字）与资料包匹配。
3. 高置信度的字段直接填，按页面/区块分批进行；遵守网站要求的格式（如日期格式、手机号是否带区号）。
4. 没把握或资料包里没有的字段留空，攒成一组问题一次问用户，不要一个字段问一次。
5. 每填完一页/一个区块，重新 snapshot 回读核对填入值，检查页面报的校验错误，修正后再进下一页。
6. 上传文件只用资料包里登记的路径，上传前报一句文件名和用途。
7. 到最终确认页时，汇总关键条目：填了什么、选了什么、费用多少、有哪些声明、还有什么没确定。
8. **停在提交按钮前**，等用户明确确认。用户笼统说过"帮我报名"不等于授权提交，确认必须针对当前页面的具体动作（例如"确认提交这份报名并支付 99 元"）。
9. 提交后截图或回读结果页，记录报名号、状态、后续步骤和截止时间。

## 强制暂停点

以下动作停下来，让用户本人操作或逐项明确确认后才继续：

- 输入密码、短信/邮箱验证码、验证码图片（CAPTCHA）、支付卡号 —— 这几类**始终由用户本人输入**，不代填
- 登录、注册账号
- 勾选法律声明、承诺书、隐私条款、营销同意
- 电子签名
- 最终提交报名/申请
- 任何付款动作
- 取消、撤回、修改已提交的报名

## 敏感信息纪律

- 个人数据只用于当前报名页面，不发往其他站点，不放进 URL 参数
- 不把证件号、验证码、支付信息写进日志、代码、笔记或本 skill 文件
- 进度汇报和总结里对证件号、手机号做掩码（如 `3701**********1234`）
- 页面若要求远程控制软件、礼品卡、加密货币、无关证件，视为诈骗信号，立即停下告知用户

## 异常处理

- 需要登录：请用户在浏览器里自己登录，登录完说一声再继续
- 出现验证码：交还用户处理，完成后继续
- 页面刷新或掉状态：先 snapshot 检查现状，确认哪些已保存，不要盲目重填
- 可能重复提交时：先查是否已有成功记录再决定重试
- 网站临时改了费用、声明或已填值：停下来指出变化，等用户表态

## 结束时报告

明确说出四种结局之一：已填好等用户确认提交 / 已提交成功（附掩码后的确认信息和后续步骤）/ 被阻塞（说清需要用户做什么）/ 因页面可疑或与要求不符而停止。页面没有可靠的成功提示时，不要说报名成功了。
